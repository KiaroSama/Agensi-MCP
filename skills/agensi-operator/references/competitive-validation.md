# Competitive Validation: Explain Stronger Uptake Without Inventing Sales

Use when asked why some competing Agensi offers appear more successful, or to extract useful product-design lessons. This workflow validates public market signals, not customer willingness to pay or actual sales. Refresh relevant offers before each decision; source baseline2026-10-10.

## Matched comparison

1. Pick one buyer job and inspect three alternatives: stronger-uptake paid offer, same-job low-uptake paid offer and competent free/simple-prompt substitute.
2. Compare the promised artifact, precise input, setup/permissions, evidence/sample, maintenance, current price and listing age. A similar title can hide a different job or plan-only scope.
3. Separate observations from explanations. Installs/prices/age are observed; "editable artifact caused purchases" is an unproven hypothesis. Exposure, history, distribution and audience remain confounders.
4. Translate one plausible differentiator into an original task contract and acceptance test. Stop if the free alternative already meets it or if required expertise/data/tools are unavailable.
5. Report a validation priority and the next evidence needed. Actual payment proof requires settled transaction/buyer evidence; do not substitute interviews, bounties or installs for it.

## Fresh comparisons and useful lessons

| Observed offer contrast | Useful hypothesis to test | Counterexample / reason not to overclaim |
|---|---|---|
| Structured incident review has stronger uptake than some similarly priced, evidence-rich drafts | Make timeline/source/cause/action ownership an inspectable artifact with low input friction | An equally concrete evidence-trail offer has little uptake; structure alone cannot explain demand, exposure unknown |
| Narrow dataset delivery has stronger uptake than some same-price dataset/architecture alternatives | Sell a completed labeled/validated dataset job, not merely an architecture essay | A multi-skill eval bundle has some uptake; narrow versus broad is not a universal rule, actual output untested |
| Editable builder implementation has stronger uptake than recent plan-only alternatives | Final native/editable result may add more value than another implementation plan | Major age differences; no causal evidence or verified fidelity; setup, write permissions and rights matter |
| Popular free diagnostic/writing offers compete with paid general versions | Paid edge must beat a competent free/prompt baseline on outcome/rework | Free price does not guarantee adoption either; install count doesn't reveal willingness to pay |

## Five design improvements to carry into an original skill

- **Finished result:** exact file/patch/editable output with integrity checks; honestly label analysis-only output instead of calling it executed.
- **Repeated job:** one explicit trigger/input/output, with meaningful non-goals and error cases rather than a universal expert persona.
- **Demonstrated edge:** same-input baseline and holdout acceptance; equal outcome means no demonstrated paid advantage.
- **Low friction:** disclose host/tool/account/API/privacy/setup costs before proposing cloud automation or subscription.
- **Observable trust:** real examples, source traces, truthful tested/not-tested compatibility, uncertainty and bounded approvals; a biography/scan/rating is not outcome proof.

## Recommendation format

```text
Job:
Observed competing alternatives and evidence/date:
Unknown sales/exposure/quality:
Proposed original differentiator:
Free-baseline gap:
Prototype and discriminating acceptance:
Cost/privacy/maintenance/rights blockers:
Decision: validate / narrow / stop
```

Do not publish a buyer-facing success claim without actual support. Do not create another vendor's paid instructions from these observations. Package only original synthesis.
